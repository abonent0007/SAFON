### Observation 1: Не-ASCII литералы в shell-командах калечатся на Windows (cp1251)

**Date:** 2026-10-14
**Session context:** Импорт батча исторических событий (76 записей) в SQLite-базу проекта SAFON; построение dedup-скрипта и правок данных через PowerShell + python.
**Skill:** fix-code (улучшение); применимо к любому навыку, генерирующему shell-команды с кириллицей (study-project, fix-code, а также общие инструкции агента)
**Type:** internal
**Phase/Area:** Порядок выполнения команд / кодировки окружения

**Issue:** Кириллические литералы, встроенные в shell-команду (`$code = @'...'@; $code | python -` и `python -c "..."`), искажаются при передаче PowerShell 5.1 -> python stdin (мохибейк: 'событие' доходит как '???????', патч-правила молча не срабатывают, поиск по кириллице даёт ложные False). При этом вывод кириллицы работает при `sys.stdout.reconfigure(encoding="utf-8")` / `sys.stdout.buffer.write(...utf-8...)`, а чтение данных из файлов — всегда корректно. Итог: два независимых инцидента в одной сессии, скрытые ошибки (патчи не применились, проверка "строки нет в файле" соврала).

**Suggested improvement:** В fix-code и связанных навыках зафиксировать правило: на Windows-окружении (cp1251) не встраивать не-ASCII литералы в аргументы команд. Надёжные паттерны: (1) любые скрипты с кириллицей создавать файлом через write-инструмент (UTF-8) и запускать `python script.py`; (2) для одноразового анализа — передавать данные через файлы или индексы/base64; (3) после выполнения всегда сверять эффект правок по данным (assert результата), а не надеяться на сообщение об успехе.

**Principle:** Если окружение имеет нестабильный канал передачи символов (консоль/пайп), данные и код с не-ASCII символами должны идти только через файлы (UTF-8) либо ASCII-безопасные представления (base64, индексы, коды символов). Плюс обязательное доказательство эффекта: проверка результата в целевой системе, а не факт "команда выполнилась".

### Observation 2: Метрика без baseline вводит в заблуждение (lift вместо сырой точности)

**Date:** 2026-10-14
**Session context:** Разработка walk-forward бэктеста системы прогнозирования SAFON; первый прогон дал «точность года 98%», что оказалось артефактом плотных данных.
**Skill:** verification-before-completion (улучшение)
**Type:** internal
**Phase/Area:** Проверка результата / определение метрик успеха

**Issue:** Сырая метрика «попадание года ±1» показала 98% и выглядела как отличный результат, хотя не отличалась от случайного угадывания: на плотных исторических данных событие почти любого года попадает в окно. Потребовалась нормализация через baseline (доля лет, покрытых событиями) — lift. Без этого шага можно было принять бесполезную метрику за доказательство точности и «улучшать» систему против шума.

**Suggested improvement:** В verification-before-completion добавить правило: любая метрика качества обязана сопровождаться baseline (chance level) и эффектом относительно него (lift / effect size). Сырые проценты без нормализации не считаются доказательством. Проверка должна явно отвечать: «насколько это лучше случайного/тривиального решения?»

**Principle:** Прежде чем объявлять метрику доказательством успеха, всегда сравнивай её с baseline: метрика, которую тривиальная стратегия воспроизводит бесплатно (98% попаданий при плотных данных), не измеряет качество модели. Lift к случайному уровню — минимальный стандарт доказательства.
